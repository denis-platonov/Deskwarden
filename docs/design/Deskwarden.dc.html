4e
Why steps, with template as a view
The step list is the editor
A password step has to carry things a string cannot show: that it is a secret, that it is gated on a masked control, that it is preceded by a field change. Those are properties of a step, so the step has to be the object on screen. Six rows for the common case is not verbose — it is the whole sequence visible at once, which is exactly what you want to check before you send a password somewhere.
The template string stays, as a second view
It is how sequences already travel — in tickets, in docs, between colleagues — so removing it would break real workflows. It is a lossless projection of the same steps, not a separate mode with its own state: parse errors block saving, and the parsed steps sit under the field so the string is never the only thing you can see. Power users paste; everyone else never opens the tab.
Safety does not live in the editor
An editor can only warn. The guarantees are at send time: the rule binds to a process, the secret step refuses a control that is not masked, sending aborts on focus change, and preflight names the actual window title rather than the rule. Rehearsal with fake data means a user can be certain a sequence is right before a real secret is ever in play.
One deliberate departure from the palette
The product is blue. Secrets are the only thing rendered in red, and caution is the only thing in amber — two semantic colours that appear nowhere else, so the hatched password step cannot be mistaken for ordinary UI.
